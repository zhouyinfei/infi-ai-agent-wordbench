# Human-in-the-Loop 与用户审批

审批由模型在任务执行中发起，审批人就是当前任务用户本人。用户在正常工作台输入目标，不需要单独提交审批单，也不需要管理员角色。

## 使用方式

1. 更新前后端并重启后端，刷新工作台。无需执行审批数据库脚本。
2. 正常输入任务。例如：“删除工具目录中的 sample.txt，这会永久删除文件，执行前请让我确认。”
3. 模型判断需要审批时，调用 `request_approval`。右侧“任务详情”栏底部出现审批卡片（窄屏固定在右下角），展示原因、操作与目标，可通过“查看详情”展开完整工具参数，并选择“批准”或“拒绝”。
4. 同意后，服务端直接执行展示的那一项工具调用，并继续原来的模型上下文；拒绝后停止整个任务，不执行该工具及后续步骤。

一般问答、计算和只读查询通常不需要审批。文件删除、重要文件覆盖、对外提交、付费及用户明确要求先确认的操作，系统提示模型先请求确认。是否发起由模型判断，不使用关键词匹配或管理员审批规则；这是模型决策机制，不是保证所有风险操作一定触发的强制策略。

支持 ReAct、Plan-and-Execute 和 Multi-Agent。Multi-Agent 仍检查目标工具是否属于当前专业 Agent 的权限，不能通过审批包装越权。联网与知识库权限也不会因用户同意审批而扩大。协调与汇总阶段沿用原有无工具约束。

## 执行语义

`request_approval` 参数：

```json
{
  "reason": "删除不可恢复，需要你确认",
  "toolName": "file_delete",
  "toolArguments": "{\"path\":\"sample.txt\"}"
}
```

批准绑定具体任务、审批编号、工具名和完整参数。请求批准后，服务端直接执行保存的调用，模型不能在批准与执行之间替换参数；一次批准不授权其他调用。模型必须单独发起一次审批工具调用；混合审批与其他工具的批次会整体拒绝，不执行其中任何操作。

任务在有界后台线程池中运行，保留原调用栈及模型消息，不通过重新运行整次任务来恢复，避免重复之前的副作用。审批等待不计入模型和工具的执行时限；单次确认最多等待5分钟，一次任务最多确认3次。会话租约额外覆盖最多15分钟等待。

任务状态：`RUNNING → WAITING_APPROVAL → RUNNING → 最终状态`，拒绝时最终状态为 `REJECTED`。普通用户只能查看和审批自己的任务，包括管理员也不能代批其他人的任务。过期或重复审批返回409，跨用户访问返回404。

工作台通过轮询更新任务，刷新页面后会尝试找回该用户在当前进程内尚未结束的任务。完成结果和审批轨迹随会话轮次保存到现有数据库；审批理由是公开操作说明，不保存模型内部思维链。

## 运行边界

当前采用单实例进程内暂停机制，等待中的调用栈不支持服务重启后恢复，也不支持无粘性路由的多实例部署。服务重启后应先核查已执行操作，再发起新任务；已执行的工具操作不会回滚。浏览器关闭不会立即取消服务端任务，等待确认到期后任务停止。

每个用户最多有一个未结束任务，后台池最多8个运行任务和16个排队任务，最多保留128个任务快照。结束快照30分钟后可在新任务提交时清理。模型和工具调用仍受原有执行预算约束。旧版同步执行接口保留兼容，不提供交互等待能力；需要审批的客户端应使用下面的工作台任务API。

如果你已经执行过前一版的 `004_approval.sql`，其表不再使用，可保留，当前功能不依赖该表。

## API

所有接口要求 Bearer 登录，身份只取自服务端认证上下文。

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| POST | `/api/agent-tasks` | 提交普通任务：`goal、mode、conversationId、modelId、useKnowledge、useNetwork` |
| GET | `/api/agent-tasks` | 查询本人当前未结束的任务 |
| GET | `/api/agent-tasks/{id}` | 轮询状态、待确认操作和最终结果 |
| POST | `/api/agent-tasks/{id}/decision` | 本人提交 `approvalId、approved`，无任务参数替换入口 |

不需要管理员审批接口、任务审批表或手动选择审批模式。
